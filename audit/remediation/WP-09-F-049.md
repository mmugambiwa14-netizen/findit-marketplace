## 2. The six reconciled, and why each moved the way it did

### `34` — two brand contracts asserting opposite things

`tests/brandLegalEmailFounderContracts.test.mjs:53` required `findit-brand-mark`, six `findit-*.png`
rasters under `src/assets/brand/`, and a `findit-icon-32.png` favicon. `tests/peekaListingBrandContracts.test.mjs`
requires the opposite. **Both could never be green at once** — the clearest instance of the finding.

Removed, because brand identity must have **one** authoritative contract and
`peekaListingBrandContracts.test.mjs` is it (F-002/WP-07 will extend that one to the whole `src/` tree).

Two things were **not** discarded with it:

- `assert.match(shell, /BrandLogo/)` across TopNav, SiteFooter, AuthLayout and AdminSidebar — that assertion
  was never about *which* brand, so it survives as its own test.
- `assert.match(pageMetadata, /apple-touch-icon/)` — a **legitimate, still-unmet** requirement. Deleting it
  would have silently dropped coverage, so it **moved to `tests/webAppManifest.test.mjs`**, which is the
  authoritative install-metadata contract and F-017's named spec. It is strengthened there: the link must
  exist, resolve to a file on disk, and be a PNG (iOS rejects SVG). **It fails, correctly** — F-017 is
  unfixed and blocked on assets.

### `508` — a test *and* a product defect

Asserted the seller queue tells sellers their upload *"remains pending while the video is processed and
moderated"* and *"becomes answered automatically after approval"*. The MVP removed human Peek moderation
(`REMEDIATION-PROMPT.md` §2.3).

Checking the component rather than assuming revealed the copy **is still shipped**:

- `src/components/peekThreads/BuyerPeekRequestsQueue.jsx:277` — *"The accepted request remains open while the
  video is uploaded, processed and moderated. It becomes answered only after approval."*
- `:193` toast — *"Response Peek uploaded. It will answer this request automatically after approval."*

So the test was failing on **wording drift between two encodings of the same removed step**, and the product
still promises sellers an approval gate that does not exist. Inverted the assertion to
`assert.doesNotMatch(queue, /moderat/i)` and `/after approval/i`, which makes this test the **proving test
for F-059** (below). It stays red until that copy is fixed — deliberately.

### `696` — value versus label

`AdminReports.jsx:148` is `<SelectItem value="tour">Peeks</SelectItem>`. The **value** stays `tour` because
it is a database enum; only the operator-facing **label** was rebranded. Test updated to the current labels
(`Peeks`, `Remove reported Peek`, `Dismiss report and restore Peek`) while keeping the `value="tour"`
assertion intact.

### `698` — a security assertion that had to be re-pointed, not deleted

This is a security test, so removing an assertion needed proof the control still exists. It required
`AdminReports.jsx` to contain `featureFlags.tours || featureFlags.toursPreview`; the page no longer
references feature flags at all.

The gate **moved into the service**, `src/services/listingToursService.js:148-152`:

```js
function requireTourAdministration() {
  if (!featureFlags.tours && !featureFlags.toursPreview) {
    throw new Error('Tour administration is not enabled in this build');
  }
}
```

and `getAdminTourReviewAccess()` (`:358`) calls it first. That is **strictly stronger** than the page-level
check it replaced: a UI condition is bypassable, a service-level throw on every admin Tour call is not. The
assertion was re-pointed at the real control instead of dropped.

### `707` — the workflow was right and the test was stale

Required `VITE_FEATURE_INTERNATIONAL_LISTING: "true"` in `deploy-staging-pages.yml`, which sets `"false"` —
as does `release-candidate-gates.yml:33`. The MVP is **Zimbabwe-first**, so `false` is the decision, not a
regression. The other four flags in that list are genuinely `"true"` and were left alone. Test now asserts
the flag is `"false"`, pinning the decision rather than contradicting it.

### security `31` — a correctly guarded tree failing a naive regex

Asserted `/<ProtectedRoute[^>]+requiredRole="admin"/`. `src/App.jsx:199` is:

```jsx
<Route element={<ProtectedRoute unauthenticatedElement={<SignInRedirect />} requiredRole="admin" />}>
```

`[^>]+` cannot cross the `>` inside `<SignInRedirect />`, so a **properly guarded** admin tree failed.
Phase 4 had already verified all 10 admin routes are nested under this boundary with server-side role
resolution — confirming the audit's read that this was a stale assertion, not a regression.

Replaced with `/<ProtectedRoute(?:(?!<ProtectedRoute)[\s\S])*?requiredRole="admin"/`. The guard is *no other
`<ProtectedRoute` may intervene*, which proves the prop belongs to the nearest preceding element. Bounding on
`>` or `/>` cannot work here — the sibling prop contains both.

## 4. Findings registered, not fixed here

Three defects were catalogued while classifying. None is in the audit's original 56; all are real, and all
are left red with their tests intact.

- **F-059** (P2) — seller-facing UI promises a Peek moderation/approval step the MVP removed.
  `BuyerPeekRequestsQueue.jsx:193,277`. Proving test already written (`508`).
- **F-060** (P2) — `buyer-journey-certification.yml` does not normalize `package-lock.json` before install,
  which the other locked workflows do. Supply-chain hygiene.
- **F-061** (P2) — `pages-preview.yml` uses `actions/checkout@v4`, a **mutable tag**, where every other
  workflow pins an immutable commit SHA. Supply-chain risk: a moved tag changes what CI executes.

`F-060` and `F-061` are owned by **WP-02**. Neither was caused by this session's workflow edits — both
name files this branch has not modified.

## 5. Deliberately not done

- **`every configured Supabase email uses the classic FindIt template family` was left alone.** It passes,
  and it asserts FindIt branding across 13 email templates — squarely **F-001/WP-07** (brand sweep), not
  F-049. Changing it here would have pre-empted a package that has to settle the copy first.
- **`AdminTourQueue.jsx` was not touched**, despite `698` revealing that `getAdminTourReviewAccess` is now
  only reached from it — and F-010 records it as an **orphaned component with zero importers**. If that
  holds, admin Tour review media may be unreachable from the live UI. Flagged for F-010/F-052; out of scope
  here.
- **No product code was changed**, including the F-059 copy. One finding per commit (rule 4).
