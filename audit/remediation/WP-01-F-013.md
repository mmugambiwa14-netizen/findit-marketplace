## 1. The finding, re-confirmed before editing

*A single early gate failure causes lint, all four typechecks, the build, contracts and internal
certification to skip.*

Reproduced on the working tree before any change:

```
$ node ./scripts/verify-sql-boundary.mjs
SQL boundary verification failed:
- 20260807020000_peek_request_fulfilment_lifecycle.rollback.sql contains destructive table/data rollback statements
exit=1
```

The rejected statement is `supabase/rollback/20260807020000_peek_request_fulfilment_lifecycle.rollback.sql:11`:

```sql
drop table if exists public.peek_request_fulfilments;
```

matched by `scripts/verify-sql-boundary.mjs:72`:

```js
if (/\bdrop\s+table\b|\btruncate\b|\bdelete\s+from\b/i.test(executable))
  failures.push(`${name} contains destructive table/data rollback statements`);
```

That step is #10 in `.github/workflows/release-candidate-gates.yml` (`:100-101`). Steps 11, 13, 14 and
16–24 then reported `conclusion=skipped`, including `Run all contracts`, `Lint application`,
`Typecheck application`, `Build production application` and `Run reproducible internal certification`.

### New evidence found while confirming

Two things the audit did not record, both relevant:

1. **Why only this rollback trips the rule.** `migrationFiles` is filtered by `/^\d{4}_.+\.sql$/`, so
   timestamp-prefixed migrations (`20260807020000_…`) are **excluded** from the sequence and release-tip
   checks. But the destructive scan filters rollbacks by `Number(file.slice(0, 4)) >= 40`, and for a
   timestamp prefix that reads `"2026" >= 40` → **included**. The numeric-prefix heuristic captures
   timestamped rollbacks by accident.
2. **`migration-gates.yml` has the identical cascade** — `Verify SQL migration boundary` at `:66-67`
   followed by lint, three typechecks, contracts, Base44 verification and build. Fixing only
   `release-candidate-gates.yml` would have left F-013 half-closed, so both are fixed here.

## 2. Decision on the rollback-versus-policy conflict

The spec required choosing **(a)** allow `drop table` for a table the paired migration created, or
**(b)** rewrite the rollback non-destructively, and justifying the choice.

**Chose (a).** The paired migration `20260807020000_peek_request_fulfilment_lifecycle.sql:3` contains:

```sql
create table if not exists public.peek_request_fulfilments (
```

The rollback drops exactly that table. **That is the correct reversal, not data loss** — before the
migration ran, the table did not exist. Option (b) would produce a capsule that does *not* reverse its
migration, leaving an orphan table behind: a worse rollback, adopted only to satisfy a rule that was never
aimed at this case.

**Rejected a third option** that looked tempting: fixing the `>= 40` prefix heuristic so timestamped
rollbacks are excluded from the scan. That would have exempted *every* timestamped rollback from the
destructive check — weakening a control to make a gate pass, which operating rule 5 forbids.

### Keeping the exemption narrow

The exemption is scoped to **tables the paired migration provably creates**, and nothing else:

- A drop of any table the migration did not create → still fails.
- `truncate` and `delete from` → still fail, in every form, including on paired tables.
- No paired migration on disk → **no exemption** (fails closed).
- `create table` appearing only inside a migration comment → grants no exemption.
- `drop table a, b;` (multi-target) → not exempted. Parsing a table list correctly is not worth the risk
  in a gate that guards production data, so only the single-target form qualifies.
- Quoted identifiers follow PostgreSQL case semantics — unquoted fold to lower case, quoted do not — so a
  migration creating `"MixedCase"` does not license dropping `mixedcase`.

## 3. What changed

| File | Change |
|---|---|
| `scripts/lib/sqlRollbackBoundary.mjs` | **New.** The destructive-statement rules, extracted as pure functions so they can be tested directly. Follows the existing `scripts/lib/` convention (`activeV1SourceGraph.mjs`, `auth-config-policy.mjs`, …). |
| `scripts/verify-sql-boundary.mjs` | Imports those rules instead of inlining them; reads the paired migration per rollback and passes it to the check. |
| `.github/workflows/release-candidate-gates.yml` | `id: install` on the npm ci step; `if: ${{ !cancelled() && steps.install.outcome == 'success' }}` on **16** independent verification steps. |
| `.github/workflows/migration-gates.yml` | Same treatment, **12** steps. |
| `tests/sqlRollbackBoundary.test.mjs` | **New.** 12 behavioural tests — 9 of them about keeping the exemption narrow. |

### Why guard on `steps.install.outcome`, not `always()`

`if: always()` would run each verification step even when `npm ci` had failed, producing a wall of
identical "command not found" failures that hide the real cause. Guarding on the install step's outcome
means the verification steps run **independently of each other** but still stop as a group if their shared
prerequisite failed.

`!cancelled()` rather than `always()` so a cancelled run stops promptly instead of grinding through every
gate.

**The job still fails if any step fails.** A step with an `if:` condition that runs and fails is a failed
step, and no `continue-on-error` was added anywhere. The change makes the pipeline report *more* failures,
not fewer — that is the point.

Foundational steps (checkout, lockfile normalisation, Node, Deno, npm ci) are deliberately **not** guarded:
nothing downstream is meaningful without them. The three artifact-upload steps keep their pre-existing
`if: always()`.

## 5. Deliberately not done

- **`deploy-staging-pages.yml` and `pages-preview.yml` were not modified.** Neither runs
  `verify:sql-boundary`, and both are short chains (validate → verify → build → deploy) with little cascade
  surface. **Their failure has a different root cause**, which is F-054 / WP-03. Changing them here would
  have been guessing.
- **`release-certification.yml` was not modified.** It collapses its checks into a single composite
  `Run static and contract gates` step, so there is no step-level cascade to break. It should be unblocked
  by the SQL fix alone; if it still fails, that is WP-02's list.
- The `>= 40` numeric-prefix heuristic is **left as it is**. It is imprecise (§1.1) but tightening it would
  narrow the scan's coverage. Worth revisiting only alongside F-056 (rollback coverage, WP-32).

## 6. Residual — what is still unproven

**The proving test the spec asks for is a CI run**, not a local one: *"a CI run in which `Lint application`,
`Typecheck application` and `Build production application` all report a conclusion other than `skipped`."*

Local evidence is `LOCAL-EXEC` and complete. The CI half is **`UNPROVEN — needs a GitHub Actions run`**
until this branch is pushed and the workflow executes.

**Expect the CI run to FAIL**, and that is the correct outcome. With the cascade broken, the previously
hidden failures become visible for the first time: the 10 typecheck errors of **F-014** and the 15 failing
tests of **F-049**. A red run whose steps all *executed* is exactly what success looks like here — the
pipeline can finally tell the truth. Driving it green is **WP-02**.
